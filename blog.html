1 min read 7 Sep 2026 Terraform

Terraform blocks, without the noise

A Terraform file is not a script. It is a stack of blocks — labelled containers that declare intent. Once you see that, HCL stops looking like syntax and starts looking like a filing system.

Every block has a type, optional labels, and a body. The type tells Terraform what kind of object you mean. The labels name it. The body is the contract: arguments in, attributes out. That pattern repeats from the first provider to the last output.

main.tf block anatomy 
# type        labels              body
resource "aws_s3_bucket" "logs" {
  bucket = "app-logs-${var.env}"
  tags   = { managed_by = "terraform" }
}

Start with four blocks and you can ship real infrastructure. Everything else is a refinement of the same idea.

terraform / provider
Who you talk to, which versions you pin, and where state lives. This is the frame, not the picture.
resource
The thing Terraform will create and keep. Address it later as aws_s3_bucket.logs.
variable / output
The public contract. Inputs you can change without rewriting the module. Outputs other stacks can consume.

Data blocks are lookups, not creates — they read an existing VPC, AMI, or secret so your config stays honest. Module blocks are folders you trust: same block shape, just pointing at someone else’s resources. Locals are the sticky notes you do not want to repeat.

If a plan looks chaotic, it is usually because blocks are mixed: a resource doing a data source’s job, a variable that should have been a local, a module hiding a one-off. Keep each block doing one job and Terraform stays readable under pressure.

Treat blocks as a filing system, not a language quiz. Name clearly, pin versions, and let Terraform own the lifecycle. The rest is just repeating that pattern until the pipeline is boring — which is the point.
